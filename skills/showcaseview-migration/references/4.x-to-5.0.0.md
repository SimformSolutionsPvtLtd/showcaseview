# showcaseview: 3.x / 4.x → 5.0.0

Requires Dart ≥ 3.0.0. One change breaks the build; one deprecation needs
planned work; one change compiles but behaves differently.

| Change | Effect |
|---|---|
| `Showcase.withWidget` no longer has `height` and `width` | Compile error |
| `ShowCaseWidget`, `ShowCaseWidget.of(context)` and `activeTargetWidget` deprecated; removed in 6.0.0 | `deprecated_member_use` warnings; still work in 5.x |
| The `GlobalKey` is no longer attached to the `Showcase` widget | `key.currentContext` / `key.currentWidget` are `null` |

## 1. `Showcase.withWidget`: remove `height` and `width` (breaking)

The tooltip is measured from `container` now. Delete both parameters and give
the container its own size when it needs one.

```dart
// Before (2.0.0 – 4.x)
Showcase.withWidget(
  key: _one,
  height: 80,
  width: 140,
  container: const Text('Custom tooltip'),
  child: const Icon(Icons.star),
)

// After
Showcase.withWidget(
  key: _one,
  container: const SizedBox(
    width: 140,
    height: 80,
    child: Text('Custom tooltip'),
  ),
  child: const Icon(Icons.star),
)
```

Look at each custom tooltip afterward: `container` is drawn as is, with no
background, padding or arrow.

## 2. `ShowCaseWidget` → `ShowcaseView` (deprecated, plan it)

In 5.x, `ShowCaseWidget` is a thin wrapper that registers a `ShowcaseView` for
you. The code keeps working, but every use is deprecated and 6.0.0 removes it.
Moving is mechanical:

| Before | After |
|---|---|
| `ShowCaseWidget(builder: (context) => X(), <options>)` | `ShowcaseView.register(<options>)`, and use `X()` directly |
| `ShowCaseWidget.of(context).startShowCase(keys, delay: d)` | `ShowcaseView.get().startShowCase(keys, delay: d)` |
| `ShowCaseWidget.of(context).next(force: f)` / `.previous()` / `.dismiss()` / `.completed(key)` | same method on `ShowcaseView.get()` |
| `ShowCaseWidget.of(context).hideFloatingActionWidgetForKeys(list)` | `ShowcaseView.get().hideFloatingActionWidgetForKeys(list)` |
| `ShowCaseWidget.activeTargetWidget(context)` or `state.getCurrentActiveShowcaseKey` | `ShowcaseView.get().getActiveShowcaseKey` (the deprecation message names `getCurrentActiveShowcaseKey`; the real member is `getActiveShowcaseKey`) |
| `state.isShowCaseCompleted`, `isShowcaseRunning`, `hiddenFloatingActionKeys`, `autoPlay`, `autoPlayDelay`, `enableAutoPlayLock`, `enableAutoScroll`, `enableShowcase`, `disableBarrierInteraction`, `disableMovingAnimation`, `disableScaleAnimation`, `scrollDuration`, `blurValue` | same names on `ShowcaseView.get()` |
| (automatic unregister when the widget left the tree) | **you** call `unregister()` in `dispose` |

Every `ShowCaseWidget` option keeps its name on `ShowcaseView.register`:
`onStart`, `onComplete`, `onFinish`, `onDismiss`, `autoPlay`, `autoPlayDelay`,
`enableAutoPlayLock`, `blurValue`, `scrollDuration`, `disableMovingAnimation`,
`disableScaleAnimation`, `enableAutoScroll`, `disableBarrierInteraction`,
`enableShowcase`, `globalTooltipActionConfig`, `globalTooltipActions`,
`globalFloatingActionWidget`, `hideFloatingActionWidgetForShowcase`.

### Where to register

Register where the `ShowCaseWidget` sat:

- `ShowCaseWidget` around the whole app (`MaterialApp(home: ShowCaseWidget(...))`
  or above `MaterialApp`): call `ShowcaseView.register(...)` once in `main()`
  or in the app's `State.initState`. No `unregister`.
- `ShowCaseWidget` around one screen: register in that screen's
  `State.initState`, keep the returned instance and call `unregister()` in
  `dispose`. Register **before** the first `build` that creates `Showcase`
  widgets, otherwise they throw "No ShowcaseView is registered".

```dart
// Before (4.x)
class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: ShowCaseWidget(
        autoPlayDelay: const Duration(seconds: 3),
        onFinish: () => debugPrint('done'),
        builder: (context) => const MyPage(),
      ),
    );
  }
}

class MyPageState extends State<MyPage> {
  final _one = GlobalKey();
  final _two = GlobalKey();

  @override
  void initState() {
    super.initState();
    WidgetsBinding.instance.addPostFrameCallback(
      (_) => ShowCaseWidget.of(context).startShowCase([_one, _two]),
    );
  }

  void onClose() => ShowCaseWidget.of(context).dismiss();
}

// After (5.0.0+)
class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(home: MyPage());
  }
}

class MyPageState extends State<MyPage> {
  final _one = GlobalKey();
  final _two = GlobalKey();
  late final ShowcaseView _showcaseView;

  @override
  void initState() {
    super.initState();
    _showcaseView = ShowcaseView.register(
      autoPlayDelay: const Duration(seconds: 3),
      onFinish: () => debugPrint('done'),
    );
    WidgetsBinding.instance.addPostFrameCallback(
      (_) => _showcaseView.startShowCase([_one, _two]),
    );
  }

  @override
  void dispose() {
    _showcaseView.unregister();
    super.dispose();
  }

  void onClose() => _showcaseView.dismiss();
}
```

### Scopes: two tours alive at once

Each `ShowCaseWidget` used to be its own instance, found through the
`BuildContext`, so a pushed screen with its own `ShowCaseWidget` never clashed
with the screen below. `ShowcaseView` instances are found by a **scope name**
instead, and the default name is shared:

- Two screens that are alive together (one pushed over the other) must use
  different scopes. The second `register` with the same name replaces the
  first, and either `unregister` removes the scope for both.
- For the pushed screen: `ShowcaseView.register(scope: 'detail')`, pass
  `scope: 'detail'` to each `Showcase` on that screen, call `unregister()` on
  dispose. Without `scope:`, a `Showcase` built after a named registration
  joins that named scope.
- `ShowcaseView.get()` returns the **active** scope, which is the last one
  registered or started. Prefer the instance `register` returned for the
  current screen over `get()` when a second scope may exist.
- If the screen below must resume its tour after the pushed screen pops,
  unregister the pushed screen's scope first, then start the tour again.

### Widgets that only had a `BuildContext`

Stateless widgets and callbacks that used `ShowCaseWidget.of(context)` don't
need a context anymore: call `ShowcaseView.get()`. The builder passed to
`globalFloatingActionWidget` still receives a `BuildContext`; use
`ShowcaseView.get().dismiss()` or the screen's instance inside it.

## 3. The key is no longer attached (behavior change)

Until 4.x the `GlobalKey` given to `Showcase` was the widget's own key, so
`key.currentContext`, `key.currentWidget` and `key.currentState` worked and
code used them to check that a target was on screen or to read its size. In
5.0.0 the key is only an identifier for the tour: those getters return `null`.

Search for `.currentContext` and `.currentWidget` on any key that is passed to
`Showcase`. To check that a target is mounted, use (5.1.0+)
`ShowcaseView.get().isTargetRendered(key)`; to skip missing steps, register
with `skipIfTargetNotPresent: true`. To measure the widget, attach a separate
key to the child.

## New in 5.0.0, no migration needed

Multi showcase (same key on several `Showcase`s), `TooltipPosition.left` and
`.right`, `targetTooltipGap`, `toolTipMargin` on `Showcase.withWidget`,
per-step `autoPlayDelay`, `onDismiss`, `description` is optional when `title`
is set, and `TooltipActionPosition.insideLeft` / `insideRight`.

## Check

`flutter analyze` shows no `deprecated_member_use` for showcaseview. Run
every tour: it starts, advances, goes back, finishes, and the overlay is gone
afterward. Open and close each screen twice and confirm the tour still starts
the second time (a missed `unregister` or a shared scope name shows up here).
